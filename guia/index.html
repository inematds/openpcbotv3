Em resumo

O openpcbotv3 é um assistente pessoal que você usa pelo Telegram, pelo painel Jarvis ou por outros canais habilitados. Ele organiza pedidos em uma fila, mantém memória e executa tarefas com ferramentas. Você pode escolher entre as assinaturas Claude Code e Codex por chat, mantendo o Codex como padrão atual. Para usar a execução por assinatura, é preciso instalar o sistema e autenticar os CLIs desejados.

O que é

Sucessor do openpcbot v2, desenhado a partir da dor real

O v2 funciona, mas é um monólito sem fila, sem custo por chamada e sem gestão do Ollama, com dois travamentos por falta de RAM em agosto. O v3 pega o que já estava pronto e testado em outros repos locais e monta por camadas.

🧱 Fila de verdade

Claim atômico, lease com heartbeat, backoff, idempotência e drain gracioso, portados do inemaccbot com os 107 testes originais. Lanes por tipo de trabalho, um Claude / Codex por vez.

🧠 Cérebro em PT-BR

Memórias com salience e decaimento, busca por FTS5 mais vetor bge-m3, consolidação noturna que detecta contradições e um vault curado que só grava com a sua aprovação.

💸 Custo e RAM sob controle

Toda chamada de LLM passa por um único gateway: tier local → barato → premium, orçamento mensal com trava, e preflight que recusa carregar modelo grande sem 40 GB livres.

Como funciona

O caminho de uma mensagem

Canais só traduzem para um barramento de eventos. O orquestrador classifica com um modelo local pequeno antes de gastar qualquer token na nuvem.

Telegram / CLI / HTTP→ Bus→ Roteador (llama3.2)→ Memória (3 camadas)→ Resposta direta local ou agente por Claude/Codex→ Guarda de segredos→ Chat
1

Roteador

Devolve JSON com rota, agente e tier. "direto" para conversa; "agente" quando precisa de arquivo, shell, repo, web ou skill.

2

Gateway de LLM

Orçamento → provedor → preflight de RAM → chamada → custo em chamadas_llm. Ollama custa zero, mas conta tokens e tempo.

3

Fila

O job roda na fila com Claude Code ou Codex pela assinatura, conforme a escolha do chat. A resposta e o uso registrado voltam ao canal de origem.

4

Aprendizado

Cada turno vira memória. Fato durável gera proposta para MEMORY.md / USER.md; você aprova com um comando.

Seu Jarvis com várias assinaturas

Se uma assinatura atingir o limite de uso, você pode escolher a outra para os próximos pedidos. O openpcbotv3 já aceita Claude Code e Codex pela assinatura, com seleção manual por chat.

Você escolhe o motor→O pedido entra na fila→Claude ou Codex executa→A resposta volta ao mesmo chat

O que está configurado

  • Padrão: Codex pela assinatura, modelo gpt-6.1-sol, esforço medium.
  • Alternativa: Claude Code pela assinatura, com modelo e esforço definidos para cada agente.
  • Escopo: a escolha vale para este chat e para os pedidos criados depois da mudança. O trabalho já enfileirado mantém o motor original.
  • Continuidade: cada motor tem sua própria sessão. Ao trocar, uma nova sessão recebe o pedido original na continuação por job e o contexto recente disponível. Não é uma transferência integral da conversa.

Exemplo: o Codex ficou sem cota. Espere o pedido atual terminar ou confirme sua situação; depois selecione Claude e continue pelo ID do job.

/status 12345
/motor claude
/job 12345 continue de onde parou

Não é preciso reiniciar o bot para mudar o motor. Cada assinatura precisa ter login válido e disponibilidade próprios. Comandos, arquivos e conectores dependem das ferramentas habilitadas em cada executor.

Configuração e conferência local

O arquivo config/agentes-ia.yaml guarda o padrão. A preferência do chat tem prioridade; use /motor padrao para seguir o arquivo novamente.

motor: codex
codex:
  modelo: gpt-6.1-sol
  esforco: medium
npm run ia -- ver
npm run ia -- validar

Esses dois comandos apenas leem e validam a configuração: não chamam modelos, não testam login e não verificam saldo. Os CLIs usam assinatura; a adaptação não habilitou novas APIs de modelos.

E se a troca fosse automática?

É uma proposta para a próxima etapa, ainda não implementada. O código do bot pode detectar um erro explícito de limite do Codex e escolher Claude sem pedir ao Codex que tome essa decisão. A decisão por regras não consome tokens de IA nem exige cota restante no Codex.

  1. O executor recebe a recusa por limite de uso e classifica o erro por código, tipo ou mensagem conhecida.
  2. O bot marca aquele motor como temporariamente indisponível e verifica se a alternativa está configurada e tem as ferramentas necessárias.
  3. Antes de retomar, confere o progresso e os efeitos externos já realizados. Uma publicação ou envio concluído não pode ser repetido só porque houve uma falha depois.
  4. O bot abre uma sessão no outro motor com o contexto salvo, registra a troca e avisa no chat.

Sem tokens para decidir não significa execução sem consumo. A chamada recusada pode já ter executado parte do trabalho; conferir a disponibilidade por uma nova chamada também pode consumir cota. O Claude usará a própria assinatura para continuar e receber o contexto salvo. Se os dois estiverem limitados, ou o estado de uma ação externa for incerto, o fluxo deve aguardar ou pedir intervenção.

Retomada automática exige registro de progresso independente do modelo. Hoje não há troca automática por cota. API como agente executor, com shell e conectores, também não está pronta; os adaptadores antigos de mensagens não equivalem a esse agente completo.

Operação e limites · Plano completo, sujeito a aprovação

Pré-requisitos

O que precisa estar no ar

Tudo local. As API keys compartilhadas são lidas em runtime do .env do v2; o v3 só precisa do próprio token de bot.

Ollama como serviço

Só HTTP na 11434. Nunca um ollama serve paralelo.

# modelos usados (mesmas tags do v2)
ollama pull qwen3.8:27b
ollama pull llama3.2
ollama pull bge-m3

Node 20+ e assinatura de agente

Instale e autentique Codex e/ou Claude Code. A execução é pela assinatura do CLI; confira o login antes de usar o bot.

node -v
codex --version
claude --version

Bot próprio no Telegram

Crie no BotFather. O token do v2 é recusado no boot (dois getUpdates = 409 e bot surdo).

# ~/projetos/openpcbotv3/.env
TELEGRAM_BOT_TOKEN_V3=123456:AAH...
PORT_V3=3142
PISO_RAM_GB=40
Guia de uso · passo a passo

Do clone ao bot respondendo

Cinco comandos. Sem token de Telegram o serviço sobe mesmo assim, com HTTP e CLI.

1

Instalar e configurar

Copie o exemplo de .env e preencha só o que é do v3.

git clone git@github.com:inematds/openpcbotv3.git && cd openpcbotv3
npm install
cp .env.exemplo .env   # TELEGRAM_BOT_TOKEN_V3, PORT_V3, PISO_RAM_GB, ORCAMENTO_MENSAL_USD
2

Rodar o doctor

Checa env, Ollama e modelos, RAM, CLIs, v2 ativo, unit e teto de memória. Não muda nada.

npm run doctor
✅ mesmo modelo geral que o v2   v2=qwen3.8:27b v3=qwen3.8:27b
✅ RAM                          63.8 GB disponíveis · piso p/ carregar modelo grande: 40 GB
⚠️  TELEGRAM_BOT_TOKEN_V3        ausente — canal Telegram desligado
3

Importar as memórias do v2

Snapshot com VACUUM INTO: o banco do v2 nunca é aberto para escrita. Idempotente.

npx tsx src/cli/importar.ts
memórias do v2: lidas 308 · inseridas 291 · já existiam 17
4

Instalar o serviço

Unit de usuário com Restart=on-failure, MemoryHigh=1.5G e MemoryMax=2G. O mesmo script serve para reiniciar depois de mudar src/ ou .env.

bash scripts/instalar-servico.sh
# build + daemon-reload + enable + restart; sem sudo
journalctl --user -u openpcbotv3 -f -o cat
5

Conversar

No Telegram, ou por HTTP e CLI enquanto não há token.

npm run cli -- "/health"
npm run cli -- "lembra que eu prefiro respostas curtas"
npm run cli -- "no projeto X, conta as linhas de src/app.ts"   # vira job de agente
6

Operar pelo chat

Fila, custo, memória, tarefas e cron sem sair do Telegram. O dashboard fica em http://127.0.0.1:3142/.

/status [id]        # fila por lane ou detalhe de um job
/usage              # custo hoje/semana/mês, por tier e agente, orçamento
/health             # Ollama, RAM, RSS, fila, heartbeat, canais
/memoria lista|buscar|salvar|propostas|aprovar <id>
/tarefa add amanhã 9h revisar PR   # lembrete + resumo no /daily
/cron lista · /ollama status · /consolidar · /novo

Roadmap

Estrangulamento, não corte seco

O v3 sobe com bot próprio ao lado do v2. Nada é apagado até a paridade: todos os comandos do v2 respondendo no v3, 7 dias sem job perdido, custo semanal medido.

0–2 ✓
Esqueleto, fila, Ollama, custo, telemetriaBus, config YAML, unit com teto de memória; fila portada; gestor do Ollama com preflight; gateway de LLM com orçamento; /status, /usage, /health, alertas.
3–5 ✓
Canais, orquestrador, cérebro, tarefasTelegram/CLI/HTTP; roteador local; agente por CLI com sessão e custo real; memória PT-BR importada do v2, embeddings, consolidação noturna, vault curado; cron como jobs, heartbeat, /tarefa, /daily.
6–7 ✓
Slack, WhatsApp, dashboard, doctor, backupSlack via Web API (desligado até o corte); WhatsApp com guarda que recusa enquanto o v2 é dono da sessão; dashboard em uma página; doctor; backup noturno cifrado.
8
CorteTrocar o token de produção, v2 só leitura por 30 dias, arquivar. Só com ordem explícita. Depois: WhatsApp real em daemon separado, Slack ligado, retenção da tabela de jobs.
